# Truthful Stripe Checkout Design

## Context

The Premium purchase flow currently presents `VISA` and `G Pay` as two app-controlled payment methods. The selected identifier is carried only between Flutter pages; `SubscriptionRepository.createStripeCheckout` and the `subscription-payment` Edge Function never receive it. Both choices therefore open the same Stripe-hosted Checkout Session, and a returned session is always labelled as VISA.

Stripe Checkout can display an eligible card or wallet, including Google Pay, according to Stripe Dashboard settings, transaction eligibility, device, browser, and customer setup. That does not make the app's separate `G Pay` selector functional or reliable.

The same screen also exposes two controls without working flows: `Add another payment method` has no action, and `Download Receipt` only reports that the feature is coming soon.

## Goal

Make the Premium sandbox payment flow describe only behavior the application actually implements, without changing voucher calculation, Stripe Checkout creation, payment confirmation, loyalty rewards, or Premium entitlement activation.

## Scope

### In scope

- Remove the app-level Google Pay and VISA choices.
- Replace method selection with one truthful, non-interactive Stripe Sandbox Checkout provider card.
- Explain that the customer chooses any eligible card or wallet on Stripe's hosted page.
- Remove the inactive `Add another payment method` control.
- Remove the non-functional receipt-download control.
- Stop storing or displaying an invented payment method in `_PaymentFlowData` and on the success screen.
- Remove localization entries made unreachable by these removals and add the new provider copy in English and Vietnamese.
- Add widget regression tests for the provider card, confirmation page, and successful-return page.

### Out of scope

- Disabling Google Pay inside Stripe Checkout when Stripe considers it eligible.
- Adding native Google Pay, Stripe PaymentSheet, saved cards, recurring billing, or receipt generation.
- Changing Stripe Dashboard settings, Supabase schema, Edge Functions, voucher rules, prices, or entitlement behavior.
- Removing intentional mock data, loading placeholders, fallbacks, or unsupported-state messages outside the payment flow.

## Design

### Payment entry page

The page displays order and voucher information as before. It then shows one non-interactive provider card labelled `Stripe Sandbox Checkout` with supporting copy: `Choose an eligible card or wallet securely on Stripe.` The heading changes from a selection prompt to `Payment provider`.

The Continue button depends only on the plan being loaded. There is no selected method state, no Google Pay or VISA row, and no add-method row.

### Confirmation page

`_PaymentFlowData` contains plan, voucher, discount, final amount, and optional purchase result only. The confirmation page displays the same Stripe provider card without a Change action. Confirming still calls `createStripeCheckout` with the existing plan, voucher, platform, and web-origin payload.

### Successful return

Both direct completion and redirect-return paths create success data without an app-invented payment method. The transaction summary identifies the provider as `Stripe Sandbox`, which is known from the integration, rather than claiming VISA or Google Pay. The Download Receipt button is absent until receipt generation exists.

### Failure handling

Existing checkout-launch, returned-session synchronization, retry, Premium verification, and voucher error behavior remains unchanged.

## Testing

Widget tests must prove these user-visible contracts:

1. The entry page shows Stripe Sandbox Checkout and its hosted-method explanation.
2. The entry page does not show G Pay, VISA, the selection prompt, or Add another payment method.
3. Continue remains available once the plan loads and reaches a confirmation page that identifies Stripe without a Change action.
4. A successful returned checkout identifies Stripe Sandbox and does not expose Download Receipt.
5. Existing entitlement, synchronization retry, voucher, repository payload, and Stripe Sandbox disclosure tests continue to pass.

Each behavior change follows a red-green TDD cycle. Final verification includes targeted widget/repository tests, Flutter static analysis, and a search for removed misleading payment copy.

## Acceptance Criteria

- No Google Pay or G Pay option is rendered or referenced by the Flutter payment flow.
- No VISA-only claim is rendered or generated by the Flutter payment flow.
- The UI states that Stripe's hosted page determines the eligible card or wallet.
- No dead add-method or receipt-download control remains.
- Stripe Checkout requests and backend code remain unchanged.
- All targeted tests and static analysis pass.
